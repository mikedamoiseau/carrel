Problem (as found)
The predicate "case-insensitively match title or author" was written out five times, in three languages, and each copy loaded the whole table and filtered in the host language.

Solution (as built)
One db::query_books(conn, &BookQuery) -> Page<BookGridItem> compiling to SQL, with the id tie-break that makes paging stable living in its ORDER BY. Case folding needed a carrel_lower scalar UDF: Rust's to_lowercase() is Unicode-aware and SQLite's LOWER() is ASCII-only, so SQL alone could not reproduce the Rust predicate.

  • locality: filter rules stopped drifting ✓
  • OPDS search gained paging, ETag and 304 ✓
  • Collections gained filters ✓
  • Tests: SQL-level, no HTTP, no React ✓

Shipped 2026-09-03 — PR #142, 6 milestones, 15 files, ~+4,100/−180. Merge commit 6a03e72, full CI green on the merge commit itself.
This review found four of the five. The card originally said four copies. The fifth — the plugin host's find_books in carrel-core/src/plugins/runtime.rs — was found only by reviewing the whole branch as one change, after the per-milestone reviews had all passed. It loaded the whole table, ran the identical match in Rust, and truncated to 50 over an order with no tie-break.
It also uncovered a live wrong-results bug that this review did not spot. db::build_rule_query emitted tag rules into joins and field rules into where, while pushing every parameter onto one flat vector in rule order — so [series equals "Dune", tag contains "scifi"] ran tt1.name LIKE 'Dune' and b.series = '%scifi%'. Wrong books, no error, and preview_collection_rules counted the same wrong set, so the rule builder's own preview agreed with the bug instead of exposing it. Fixed in M6; existing collections needed no action, since the rules were always stored correctly.
Not done, written up in docs/backlog/: the desktop's Library.tsx still filters in the browser (it holds the library in memory, so the case for pushing it to SQL is weaker); the OPDS handlers still share an unextracted ETag envelope, and all_books keeps the unsaturated paging arithmetic and missing tie-break that M3 fixed for search; and get_books_in_collection_grid / list_books_grid now produce SQL identical to their query-module counterparts under a default BookQuery, so both are deletable — but they are called from the desktop IPC layer, so it needs the Tauri-side tests too.

Problem (restated 2026-09-04 — the original was wrong)
The module that exists to be shared is called — by Carrel Server, the out-of-repo consumer this review could not see. So the two copies are not "live vs dead"; they are two live renderers, one per product, and every fix lands in whichever one the author happened to be looking at.

Solution
Fold the live copy's ETag, OpenSearch and stable-updated work into core, and have the web module call it.

  • Deletion test: deleting core's copy changes nothing — false, it breaks Carrel Server
  • leverage: one renderer, two products
  • 297 test lines start guarding both, not one
  • One answer to "is the id escaped?"
Confirmed by the consumer, 2026-09-04. The Carrel Server session was asked directly and answered with file:line evidence: it imports book_to_entry, wrap_feed, EntryUrls, FeedKind, xml_escape, mobi_ext_and_mime, cover_mime and both ATOM_* constants, pinned at v3.0.3 (c2734df, verified to be that tag's commit, and the file is unchanged since). It has no renderer of its own — every OPDS byte it serves comes from core. So the escapes in core's book_to_entry are load-bearing for a live product, and the ones that matter most are title, author and description: tenant-controlled metadata read out of uploaded EPUB/PDF files. Dropping them would be an XML-injection hole, not a tidiness regression.
Two more of this review's claims were wrong. Core does have paging — wrap_feed's sixth parameter is next_href: Option<&str> and it emits <link rel="next"> (opds_feed.rs:205-213), which Carrel Server uses with the same 50-item page size. The only thing PR #142 added that core genuinely lacks is the whole-set feed ETag and the OpenSearch descriptor.
A defect found while checking, affecting the consumer. Core builds <updated> from chrono::Utc::now() (opds_feed.rs:201), so it changes on every request; the desktop copy takes updated_ts: Option<i64> and derives it from the data. Carrel Server has no feed-level ETag, so <updated> is the only freshness signal its feeds carry — and it is pure noise. Reported to them.
Escape divergence, severity corrected. Re-verified: core still binds let id = xml_escape(&book.id), the copy serving traffic still binds let id = &book.id. The core test that would catch it still passes, because nothing calls the code it tests. But the original card overstated the impact: book ids are locally-generated Uuid::new_v4() strings, so no & can occur in normal use. This is latent for the id specifically: Carrel Server confirmed its ids are server-minted Uuid::new_v4() on both write paths, with no handler accepting a client-supplied id — so it holds by construction on both sides, not by luck. The argument for this candidate is the fork, not the escape bug.
Direction settled with the consumer: fold the live copy's ETag and OpenSearch work into core, never the reverse, and keep it additive — new functions and a new options struct rather than any change to wrap_feed's or book_to_entry's existing arity, since Carrel Server pins a release tag. Any arity change needs a tag bump and a heads-up, not a silent change on main.
Shipped 2026-09-05 — PR #143, 4 milestones plus a whole-branch pass, ~+2,100/−390. Merge commit 3fe05aa, full CI green on 86ea5cc. The desktop copy is gone: 241 lines deleted, all six OPDS routes render through core, and every route is pinned byte-identical against baselines captured from the pre-adoption tree rather than from the new renderer.
The fork was hiding a live bug, which is the better argument than the fork itself. Every page of a paginated feed shared one ETag. Proven by probe before any fix: page 0 and page 1 both returned W/"1da890753598ce82", and page 1 answered 304 Not Modified to page 0's validator — an empty body for a page the client had never seen. Four comments in the tree asserted the sharing was deliberate and correct. All four were wrong and are gone.
Three claims on this card were wrong, and two of them were mine. The 0 callers correction above was the first. The second: the escape divergence is latent for collection feeds too, not only for book ids — but the shipped code could never reach it, because an unknown collection id raises QueryReturnedNoRows and answers 500 before rendering, and real ids are Uuid::new_v4(). The third was a benchmark: “15.6x faster” came from a synthetic feed whose entries were 38 bytes. On a real 50-entry page it is 2.4x (~276 µs → 114.8 µs). Caught by the consumer's session from the arithmetic alone, without running anything.
What the process caught, and what it did not. Every real defect came from reading the code or injecting a fault — never from the nine CI gates, which only ever caught slips in the fixes themselves. The whole-branch pass found what four per-milestone reviews structurally could not: a urn:carrel:* persistence-boundary warning that lived on one of two duplicate copies and was deleted along with the duplicate, leaving the id shape in core unannotated while CLAUDE.md still pointed at the file that no longer held it. Nobody removed a guardrail on purpose.

Problem
Web corrects a selection's leading whitespace before storing the offset; desktop does not, but trims the text anyway. The same drag stores two different anchors.

Solution
One module owning "where is this highlight now", with the whitespace and entity conventions as stated invariants. Both UIs keep their own renderer and stop owning the arithmetic.

  • Corrupt anchors stop being writable
  • Desktop gains the drift fallback it lacks
  • locality: one convention, one place
  • Tests: a pure table, no DOM
Verified against source. app.js:5870 computes lead and adds it; ReaderPane.tsx:1224 does not. Both then store the trimmed text, so a desktop highlight that starts on whitespace is stored shifted left by the whitespace length. The React side is also inconsistent with itself: it captures at DOM-text offsets and renders at HTML-string offsets. No test on either side reaches this.

10. IpcMetrics is opt-in, and its success field is always true

Speculative in-process
src-tauri/src/ipc_metrics.rs — 330 lines, instrumenting 15 of 156 commands
mark_error — called only from its own test

Problem
Each site hand-types a label that must match the function name, and nothing checks it. Coverage is arbitrary: start_folder_import is timed, start_files_import is not. Of the six longest command bodies, only one is instrumented.

Solution
Wrap once at the registry, deriving the label from the function name and reading success from the actual Result.

  • Coverage goes 15 → 156, opt-out not opt-in
  • Label can't disagree with the function
  • Deletion test: it currently carries no complexity
  • One test replaces 156 nobody will write
Verified. mark_error is called from nowhere but ipc_metrics.rs's own tests, so every metric recorded in production carries success: true regardless of outcome. A command that fails in 100 ms is indistinguishable from one that succeeds in 100 ms.
